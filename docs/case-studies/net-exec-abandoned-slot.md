# net_exec 超时后，谁负责归还槽位

## 问题

`net_exec_submit()` 把调用提交到网络线程执行，并允许提交方等待完成。真正棘手的不是正常完成，而是等待超时：提交方已经准备返回，队列中的请求却可能尚未开始，也可能正在回调里运行。此时如果提交方直接把槽位标为空，工作线程可能继续使用已被下一次提交复用的 `proc`、`arg` 或完成信号量；如果谁都不回收，固定的八个请求槽很快会耗尽。

我需要确认当前实现到底由谁回收，以及超时和完成竞态是否会给下一次请求留下一个未消费的信号量计数。

## 错误的直觉

一个错误直觉是把超时理解成取消：`net_exec_submit()` 返回超时，并不意味着回调一定不会运行。只有工作线程尚未开始时，它才能看到放弃标志并跳过回调；一旦 `started` 已置位，回调没有取消协议，提交方必须等待它收尾。

另一个错误直觉是把代码描述成某个枚举状态机。当前 `kernel/src/net/net_exec.c` 没有 `PENDING/RUNNING/DONE` 枚举，也没有单一原子状态字。真实协议由 `started`、`completed`、`abandoned` 三个布尔字段，加上 `proc == 0` 表示空槽共同组成，并由 `request_locker` 串行化状态检查和修改。文章若虚构更整齐的状态，反而会遮住实际竞态。

## 证据/代码路径

初始化时，`net_exec_init()` 建立容量为 8 的 `fixq`，并为每个静态请求槽创建一次初值为 0 的 `done` 信号量。提交时持锁查找 `proc == 0` 的槽，写入 `proc`、`arg`，并把三个布尔字段都清零；若入队失败，只需在锁内恢复 `proc = 0`。

入队后，提交方在 `done` 上按 `timeout_ms` 等待。工作线程从队列取出请求后先持锁检查 `abandoned`：若提交方已经超时放弃，工作线程不调用回调，直接把 `proc` 清零归还槽位。否则它设置 `started = 1`，解锁执行回调，完成后再次持锁。如果此时发现 `abandoned`，说明提交方在回调运行期间超时，工作线程清空 `proc` 且不通知；如果没有放弃，则设置 `completed = 1` 并通知 `done`，由提交方消费通知后清空 `proc`。

## 设计

我把回收责任按“谁最后确认请求不再被使用”划分。尚未开始便超时的请求，由工作线程在出队时回收，因为队列仍持有该指针；已开始后提交方不能提前复用槽位。代码检测到 `err < 0 && started && !completed` 时，先放锁，再以 `timeout_ms == 0` 无限等待完成通知。这样慢回调即使超过原超时，提交仍返回 `NET_ERR_OK`，因为操作已经开始且最终完成，不能假装取消成功。

竞态窗口也有专门处理：初次定时等待可能刚返回超时，工作线程同时已经设置 `completed` 并投递通知。提交方重新持锁看到 `completed` 后，会用非阻塞的 `timeout_ms == -1` 再消费一次 `done` 计数，然后才清空 `proc`。这一步避免陈旧通知残留到槽位下次复用。相反，`abandoned` 路径刻意不通知，因此永久绑定在槽位上的 `done` 也保持为 0。

这里的信号量生命周期与请求生命周期不同：`done` 在 `net_exec_init()` 中按槽创建，不会在每次提交后销毁；请求只重置字段并复用同一个信号量。当前模块也没有 `net_exec_destroy()`，所以代码不存在“超时线程释放信号量、工作线程随后 notify 已释放对象”的路径。代价是初始化成功后这些信号量与执行器同寿命；初始化中途失败的清理并非这套测试所证明的内容。

## 验证边界

`tests/host/test_m6b_exec.c` 用两个提交线程和一个工作线程验证请求串行执行、提交者确实等待完成，并检查回调不重叠。更关键的是慢回调测试：提交超时设为 10 ms，回调开始后被人为阻塞约 30 ms，最终断言 `net_exec_submit()` 仍返回 `NET_ERR_OK`。这覆盖了“已 started 后不得按超时回收槽位”的核心分支，并在 ASan、UBSan 和 pthread 主机实现下运行。

边界同样要说清楚：现有主机测试没有直接构造“排队期间超时、工作线程随后跳过 abandoned 请求”的独立断言，也没有穷举所有锁竞争时序。QEMU 集成测试能说明该执行器参与实际网络栈运行，但不是形式化并发证明；主机 pthread 信号量实现与 RISC-V 目标上的内核信号量也不是同一实现。因此当前证据支持代码协议和已覆盖竞态，不应扩张为任意调度器、任意硬件上的无锁或实时性保证。
